# AGENTS.md

This file provides guidance and technical context for AI agents working on code in this repository.

## Project Overview

`branch_bench` is a single-file C microbenchmark ([`branch_bench.c`](branch_bench.c)) designed to measure the real CPU performance penalties associated with branch mispredictions across modern processor pipelines.

It runs four default tests, plus two opt-in ones (5 and 6, below), comparing predictable versus unpredictable branching patterns:

1. **Test 1 — Threshold Sum**: `sum_threshold()` on a sorted vs. a shuffled copy of one random byte array (`prepare_threshold()`, so both hold the same multiset), summing elements above a threshold (`128`). Measures direct branch prediction behavior. The console and report state the actual count above the threshold per pass (`threshold_note()`; about 127/256, never called exactly 50%), and every row's result must equal `threshold_reference()`, computed from a histogram rather than the kernel's loop (`check_result()`; a mismatch exits 1).
2. **Test 2 — Bias and Ordering**: `count_decisions()` on five biases (`t2_words[]`: 1/16 `1000000000000000`, 1/4 `1000`, 1/2 `10`, 3/4 `1110`, 15/16 `1111111111111110`), each in three orders with exactly the same number of ones (periodic word, clustered ones-then-zeros, and the periodic array shuffled with `test_seed(2, b + 1, 0)`), plus constant-0 and constant-1 controls (17 rows; `measure_bias()` checks each order's ones and the periodic period with `fundamental_period()` before measuring, internal error otherwise). Per bias, periodic and clustered are each paired with shuffled (the shuffled row's trials from both pairs make its reported row); the effective cost comes from the 1/2 periodic/shuffled pair only. A bias row's label starts with its bias (`check_export.py` checks the counts against it). Needs `--size` to be a multiple of 16 (`T2_PERIOD`), else it skips. Do not predict a miss rate from the bias or claim a predictor type from these rows. Every row is checked against `ones × reps`.
3. **Test 3 — Indirect Dispatch**: One kernel, `dispatch_indexed()`, loads a precomputed index per call and calls `leaf_table[idx[i]]` through one indirect call site. For each target count T = 1, 2, 4, … 64 (`T3_COUNTS`), a cyclic sequence (`i % T`) and the same sequence shuffled (`test_seed(3, T, 0)`), both with exactly `len / T` calls to every target (`equal_target_counts()`, internal error otherwise), are one pair; the effective cost comes from the T = 64 pair. Every row's result must equal `dispatch_reference()`, the same recurrence without calls. Needs `--size` to be a multiple of 64 (`NUM_FUNCS`), else it skips. Evaluates the history-based indirect branch predictor (a plain Branch Target Buffer alone cannot learn a cycle of several targets); returns, loop branches, index loads and the accumulator dependency are part of the workload.
4. **Test 4 — Branch vs. Branchless**: Four cells, sorted/shuffled × branch/branchless, from one multiset prepared as in Test 1 (Test 4's own seed): the branch rows run Test 1's `sum_threshold()`, the branchless rows an arithmetic mask (`(u64)0 - (u64)(arr[i] > THRESHOLD)`, `sum_branchless()`). Three pairs: branch shuffled vs. sorted (the only effective-cost line, since only it runs the same instructions on both sides), and branchless vs. branch for each order (a ratio below 1 means branchless is faster). Branch and branchless run different instructions, so never call their difference a pure misprediction penalty. Every row is checked against `threshold_reference()`.
5. **Test 5 — Pattern Learnability** (opt-in): Runs Test 2's `count_decisions()` on repeating binary de Bruijn sequences of orders 5–11 (periods 32–2048, prefer-one construction, generated and checked at setup) vs. random 50% ones. Reports learnability for this kernel only; never claim a predictor capacity or history length from it. Periods 32 and 2048 are each measured as a pair with the random row (whose trials from both pairs make its reported row); periods 64–1024 run alone. Below `DB_MIN_SAMPLE` (65536) elements its summary lines (ratios, effective cost, low-miss periods) are replaced by an n/a note, because the random row repeats often enough that a predictor may learn it.
6. **Test 6 — Correlation Distance** (opt-in): `correlate_distance()` runs branch A on a random outcome, d filler branches with a constant outcome, then branch B, for d = 4, 8, … 1024. B copies A in the correlated row and is independently random in each d's reference row; each d's two rows are one measured pair (separate B buffers), and the pair's summed miss difference per valid pair gives the "Correlation used" share per d (clamped to 0–100%; n/a for a d whose pair has no valid miss counts, and no summary at all when no pair has any; each pair decides from its own trials, so a failed median row does not hide the others) and the largest d at ≥ 90%. A d with fewer than `D6_MIN_SAMPLE` (65536) blocks per pass shows n/a with a note, because A's and B's random sequences repeat often enough that a predictor may learn them; at the defaults every d has at least 261,632. Its effective cost comes from the d = 4 pair, and only when that pair reaches 65536 blocks per pass; with no d evaluated, "Largest d" shows n/a. Rows do different work (blocks × passes from a budget of `--size × --reps` branches), so they carry their own `Work` (unit "block"); compare times only within a pair. d counts filler iterations, not history bits.

A run without `-t` runs Tests 1–4 (`DEFAULT_TESTS`); opt-in tests run only when selected, so the default set stays Tests 1–4 (numbers are comparable only within one `BENCH_REVISION`; RESULTS.md is revision 1).

On Linux systems supporting `perf_event_open(2)`, the benchmark reads hardware performance counters (`PERF_COUNT_HW_BRANCH_INSTRUCTIONS`, `PERF_COUNT_HW_BRANCH_MISSES` and `PERF_COUNT_HW_CPU_CYCLES`) as one perf group, so all counts cover the same window. Any counter that fails to open is left out of the group; the console omits it and the Markdown report shows "–" for it. From the cycle and miss counts, each test reports the **Effective extra cycles per additional miss** (Σ Δcycles ÷ Σ Δmisses between its predictable and unpredictable variant over the valid pairs, signed; Test 4 uses its branch kernel's shuffled vs. sorted pair). It is omitted when either counter is missing or no pair is valid, and printed as "inconclusive" with the raw differences when Σ Δmisses is below 1000 per valid pair (`COST_MIN_MISSES_PER_PAIR`). It is workload-dependent, not a pipeline recovery latency. Counters need `/proc/sys/kernel/perf_event_paranoid` ≤ 2. When hardware counters are unavailable (e.g. non-Linux, locked down VMs/containers), it gracefully falls back to monotonic wall-clock timing (`now_ms()`). The wall-clock fallback uses POSIX `clock_gettime(CLOCK_MONOTONIC)`, so the benchmark needs a POSIX system; it does not build with MSVC.

## Build, Run, and Verification

### Canonical Run Command
```sh
./run.sh            # options are passed on, e.g. ./run.sh -n 5 -o report.md
```

The script compiles the code and immediately executes the benchmark with its arguments. It stops if compilation fails (`set -e`), so a stale binary never runs. It builds with:
```sh
gcc -std=c99 -O2 -fno-tree-vectorize -fno-if-conversion -o branch_bench branch_bench.c
```
On x86-64 it adds `-Wa,-mbranches-within-32B-boundaries,-malign-branch=jcc+fused+jmp+call+ret+indirect` (see the JCC erratum under Testing and Validation). It also passes its flags and `git describe --always --dirty` as `-DBUILD_FLAGS="\"...\""` and `-DBUILD_COMMIT="\"...\""`; the banner and report header print them when set, and always print the compiler (`__VERSION__`).

On Windows, build and run inside WSL2. [`.gitattributes`](.gitattributes) keeps the `.sh` scripts LF in every checkout, so they run there.

### Critical Compiler Flags
Both optimization flags are strictly load-bearing:
- `-fno-tree-vectorize`: Prevents the compiler from vectorizing loops with SIMD instructions, which would eliminate branches altogether.
- `-fno-if-conversion`: Prevents the compiler from converting `if`/`else` control flow into conditional move (`cmov`) instructions. Real branch instructions are required for Tests 1–3, 5, 6 and Test 4's branch rows to trigger branch prediction logic. On x86-64 and AArch64 the kernels of Tests 1, 2, 4 and 5 are asm and do not depend on it; Test 3, Test 6 and the C fallback do.

`-std=c99` enforces the C99 requirement at build time. POSIX and Linux APIs (`clock_gettime`, `localtime_r`, `fdopen`, `syscall`) are exposed by the `#define _DEFAULT_SOURCE` at the top of `branch_bench.c`, which must stay before the first `#include`. Do not replace it with `_POSIX_C_SOURCE`: that hides `syscall()` and breaks the build.

### Compiler Support
GCC is the reference compiler. Clang rejects `-fno-if-conversion` and has no equivalent flag; it builds with `clang -std=c99 -O2 -fno-vectorize -fno-slp-vectorize`. On x86-64 and AArch64 the data-branch kernels `sum_threshold` (Tests 1 and 4) and `count_decisions` (Tests 2 and 5) are each one `__asm__ __volatile__` block holding the whole function body (the `n == 0`/`n_reps == 0` exits, the pass loop and the element loop; a C guard around the asm lets Clang add `setcc` code), so they keep their branch under any compiler (`KERNEL_ASM`, `KERNEL_BACKEND` = `asm-x86_64`/`asm-aarch64`). Other architectures, and builds with `-DBRANCH_BENCH_C_KERNELS`, use the C loops (`KERNEL_BACKEND` `c`), whose branches depend on the compiler; the banner (`Kernels:`), report (`_Kernels: …_`) and export (`kernel_backend`, each kernel's `backend`) say which ran. Keep both loops inside the asm block: `asm volatile` does not stop a C loop around it from being unrolled, which duplicates the branch (`asm_unrolled_fixture.c`). Clang (18–22) still makes Test 6's C kernel `correlate_distance` branchless (`sbb`/`cmov`; `csel`/`cset` on arm64), so its Clang timings do not show the misprediction cost. When checking any build's disassembly (`objdump -d`), look for a conditional jump on the data inside the inner loop, not just for the absence of `cmov`.

### CLI Options
- `./branch_bench`: Runs Tests 1–4 (the default set) and outputs results to stdout.
- `./branch_bench -o <file.md>` / `./branch_bench --output <file.md>`: Generates a structured Markdown report matching the format used in [`RESULTS.md`](RESULTS.md) alongside the stdout stream. Its heading is the CPU model with the highest `cpuinfo_max_freq` from cpufreq sysfs (`@ 3.60 GHz`, replacing any base clock in the model name; left as-is where sysfs has no clock information, e.g. WSL2). When the cycle counter works, the console and report end with the **effective user-cycle rate during measurements** (user-mode cycles ÷ wall time over all measured trials, training runs excluded; kernel time and preemption lower it, so never call it the core clock). The header table records the compiler, followed by the build flags and commit when `run.sh` built the binary. When a counter opened only as its ARM raw event (see TODO), the banner's "Raw PMU events" line and the report's "Raw ARM PMU events" line name it; no such line means every open counter is the generic event. An existing file is overwritten (a new one is created owner-only, mode 0600), so never pass `RESULTS.md`: write a separate file and paste its `## <CPU>` section into RESULTS.md by hand, under `# NEW RESULTS` (bare metal or WSL2) or `# VPS RESULTS` (cloud VMs), not at the end of the file. Current entries use the defaults with `-n 6`.
- `./branch_bench -n <N>` / `./branch_bench --trials <N>`: Measures each variant N times (1–99) and reports the trial with the median time. Every measured trial, also with the default `-n 1`, follows one untimed training run, and paired variants alternate AB/BA. N > 1 adds the fastest–slowest range (console, and a Range column in the report) and the banner/report protocol line; `-n 1` output has neither.
- `./branch_bench -t <N>` / `./branch_bench --test <N>`: Runs only test N (1–6); repeat the option to run several. The banner and report note which tests ran. Without `-t`, Tests 1–4 run; Tests 5 and 6 run only when selected.
- `./branch_bench --hard`: Runs all six tests (`HARD_TESTS`), also when combined with `-t`. The banner prints `Tests: 1, 2, 3, 4, 5, 6 (all, with --hard)` and the report `_All tests were run (--hard), including the hard tests 5 and 6._`; runs with `-t` alone keep `(selected with -t)` / `_Only test(s) … were run._`. Collect hard results with `./run.sh --hard -n 6 -o hard.md` and paste them into their own subsection under the CPU's RESULTS.md heading: the Tests 1–4 sections are comparable with default runs, but the effective user-cycle rate line covers all six tests, so it is not.
- `./branch_bench --size <N>`: Elements per array for Tests 1/2/4/5 (blocks for Test 6) and calls per trial for Test 3 (default 4M = 4194304, max 1024M; `K`/`M` suffixes, case-insensitive, are powers of 1024). Test 2 needs a multiple of 16, Test 3 a multiple of 64 (equal calls to every target) and Test 5 a multiple of 2048 (whole periods of their patterns); otherwise the test prints a skip note (console and report) and measures nothing, and other selected tests still run. Test 6 likewise skips when `--size` < 64 or `--size × --reps` < 65664 (64 blocks of the longest distance).
- `./branch_bench --reps <N>`: Passes over the array per trial for Tests 1/2/4/5 (default 64, max 100000); for Test 6 it only scales the branch budget.
- `./branch_bench --json <file>`: Writes a JSON Lines export (schema 1, `JSON_SCHEMA`; record types `meta`, `kernel`, `variant`, `trial`, `pair`, documented in README.md) after all tests, from the measurement log. Opened at startup like `-o` (mode 0600 when new); a write or close failure prints `Error writing JSON export to …` and exits 1, and `-o` and `--json` naming the same file (equal paths, hard links, or spellings such as `a.md` and `./a.md`) is rejected with exit 1. `open_outputs()` opens both without `O_TRUNC`, compares the open files with `fstat()` (`same_open_file()`, which also fails on an `fstat` error), and only then truncates each regular file, so neither an alias nor a `--json` path that cannot be opened ever empties an existing report. Metadata is read only at export time (`cpuinfo_value()`, `cpuinfo_has_flag()`, `sysfs_line()`, `uname()`). The `kernel_descs[]` table declares each kernel's static branch sites, its revision, backend and `taken_when` (`"false"`: the asm data branch jumps, skipping the update, when the source condition is false; `null` for C kernels, where the compiler decides; declared, not measured); it holds no function pointers, because taking a kernel's address can change how GCC compiles and places the kernels (the export's `entry` is `null`). `emit_rows()` registers each row as a variant (`log_variant()`), and a test records each row's input at setup with `log_input(variant, buf, pass_items, has_cond, cond_true)` (items per pass, condition-true items per pass, FNV-1a hash of the buffer; exported in the variant record, and `--same-results`/`--different-results` compare the hashes too), so every new summary line must come from `pair_stats()`/`pair_cost()` and be reproducible by `.github/scripts/check_export.py`.
- `./branch_bench --cpu <N>`: Pins the run to CPU N (0–1023, `MAX_CPU`) in `apply_affinity()`, before `perf_init()`, through raw `sched_setaffinity`/`sched_getaffinity` syscalls (glibc's wrappers need `_GNU_SOURCE`), and reads the mask back. Only when given, the banner prints `CPU affinity: pinned to CPU N` / `FAILED to pin to CPU N (reason)` / `not supported on this system`, and the report `_Pinned to CPU N._` / `_CPU affinity request for CPU N failed: reason._` / `_CPU affinity not supported ..._`. A failure also warns on stderr and the run continues unpinned with exit status 0; never report a run as pinned without the read-back.
- `./branch_bench --seed <N>`: Base seed for every test's input (decimal, or hex after `0x`/`0X`, 0–2⁶⁴−1; default `0xdeadbeefcafe1234`). A leading zero stays decimal (`010` is 10, not octal 8): `parse_seed()` never uses `strtoull`'s base 0. The banner and report print it only when given. The banner's `Revision:` line and the report's `_Benchmark revision N._` line always print `BENCH_REVISION`; bump it whenever a change alters what is measured. Revision 2 (Stage 1 of the plan) and revision 3 (Stage 2: assembly data-branch kernels, new Tests 1–4) data are not comparable with RESULTS.md's revision 1 entries or with each other.
- Non-default sizes are visible in the banner, test headings and report header table. Results are only comparable with RESULTS.md at the defaults (`--size 4M --reps 64`).
- `./branch_bench -h` / `./branch_bench --help`: Displays usage information.

### Testing and Validation
There is no dedicated test framework or linter in this repository. Validate changes by compiling with `gcc` using the required flags (plus `-Wall -Wextra -pedantic` to catch issues) and executing the binary. `clang --analyze -std=c99 -Xclang -analyzer-werror <repo>/branch_bench.c` should report no warnings; run it from a scratch directory, because it writes a `.plist` into the current one. It finds the same kind of path-based bugs (uninitialized values, out-of-bounds reads) that SonarQube Cloud reports. SonarQube's C rules that this code has hit are listed in Code Architecture section 8. `.github/scripts/perf_test.c` tests the perf scaling and error paths without a PMU: `gcc -std=c99 -O2 -fno-tree-vectorize -fno-if-conversion -o /tmp/perf_test .github/scripts/perf_test.c && /tmp/perf_test`. It `#include`s `branch_bench.c` with `main`, `read` and `ioctl` renamed, so every `read()`/`ioctl()` in the file reaches its stubs, which serve only counter reads; a new `read()` or `ioctl()` for anything else (e.g. sysfs) needs the stubs to pass it through. `.github/scripts/check_export.py EXPORT [--report R.md] [--kernel-counts F] [--same-results|--different-results OTHER --test N]` (Python 3, standard library only) rebuilds every pair record from the trial records and, with `--report`, checks the report's table times, ranges, ratio lines and effective-cost lines against the export; It also checks every counted trial's scaled counts against its raw counts and scheduling times, the report's counter, Miss % and misses-per-item columns against the median trial, and both the resolved and the inconclusive cost lines (`cost_shown` means the line was printed), and Test 6's "Correlation used", "Largest d" and n/a lines (rebuilt from each pair's miss delta and the variant's `pass_items`; `D6_MIN_SAMPLE` is duplicated there). It also requires both variants of every pair to have equal `work` and, where recorded, equal `pass_items` and `cond_true`. Every check needs something to compare, so an empty export or report fails. `smoke_test.sh` runs it on a `-n 3` export with its report, a `--hard` export with its report and the largest legal run (`--hard -n 99 --size 64K --reps 2`, 7029 trial records), feeds it a report with one counter cell changed and one with a changed "Correlation used" figure (both of which it must reject; skipped without counters), and uses `--same-results`/`--different-results` for every test to prove that selecting another test does not change its input and `--seed` does. `smoke_test.sh` therefore needs `python3`; it also picks the `--cpu` cases from its own affinity mask, so they hold in a cpuset-limited container. Tests 1–4 check every row's kernel result against a reference computed at setup without the kernel (`check_result()`), and Test 5 validates its patterns; on a mismatch the program prints an error and exits with status 1. `perf_test.c` also tests the kernels on edge inputs (0, 128, 129, 255, one element, no elements, no passes) and the input builders.

Changes anywhere in the file can move the kernels to new addresses, which can change timings even when their code is untouched. After a change, compare the kernels' disassembly with the previous build, ignoring addresses and padding `nop`s:
```sh
objdump -d --no-show-raw-insn branch_bench | awk '/<(sum_threshold|sum_branchless|count_decisions|dispatch_indexed|correlate_distance)(\.[^>]*)?>:/,/^$/'
```
GCC may add clone suffixes such as `.constprop.0`. If kernel code changed, also compare cycles per element and effective cost per miss with the previous build (`-n 5`). No jump in a kernel may cross or end on a 32-byte boundary: Intel's JCC-erratum microcode slows such jumps on Skylake-derived CPUs, including the i5-8350U in RESULTS.md, so an unrelated edit could add or remove the penalty for some kernels. `run.sh`'s x86-64 assembler flags pad every jump, `call` and `ret` off those boundaries (`-mbranches-within-32B-boundaries` alone leaves `call`/`ret` out). `.github/scripts/check_jcc.sh ./branch_bench` lists every such jump in the kernels (a macro-fused `cmp`/`test` + `jcc` pair counts as one jump) and exits 2 if a kernel is missing, e.g. after a rename; a build with the flags must list none, and CI's x86-64 gcc job fails on any. Builds without the flags (CI's other jobs, Clang) are not checked. Padding adds only `nop`s and redundant `cs` prefixes, so the kernels' instructions stay the same.

### Continuous Integration
[`.github/workflows/ci.yml`](.github/workflows/ci.yml) runs on pushes to `main`, on pull requests and on manual dispatch. Hosted runners are VMs, usually without hardware perf counters, so CI checks correctness and codegen only, not timings. They use Ubuntu 24.04's GCC 13 and Clang 18; the gcc-latest job adds the newest GCC release, but a codegen pass in CI still says nothing about another local compiler version. GitHub's CodeQL default setup also scans the code, outside this workflow. Actions are pinned to commit SHAs, and gcovr and all its dependencies to versions and hashes in [`.github/requirements.txt`](.github/requirements.txt), which `pip-compile --generate-hashes` generates from [`.github/requirements.in`](.github/requirements.in) (run it in `.github/` under Python 3.12, CI's version; the exact command is in both files). [`.github/dependabot.yml`](.github/dependabot.yml) opens a monthly pull request when any of them, or the gcc-latest image, has a release at least 7 days old (`cooldown`).
- **gcc** (x86-64 and arm64): builds with the required flags plus `-Wall -Wextra -pedantic -Werror` (and `run.sh`'s JCC alignment flags on x86-64, where it then fails if `check_jcc.sh` lists any hit), compiles the non-perf path (`-U__linux__`), builds, runs and kernel-checks the C-kernel fallback (`-DBRANCH_BENCH_C_KERNELS`), runs `--size 64K --reps 2` with and without `--hard` (the default run skips Tests 5–6), and runs [`.github/scripts/check_kernels.sh`](.github/scripts/check_kernels.sh). It requires exactly one **data branch** in Test 1's `sum_threshold` (also Test 4's branch rows) and Test 2's `count_decisions` (also Test 5's), none in Test 4's `sum_branchless` (where `cmov`/`setcc` are allowed), exactly one indirect call in Test 3's `dispatch_indexed` (a retpoline or indirect-thunk build, which turns it into a direct call to a thunk, fails by design), `leaf_0`–`leaf_63` at 64 distinct addresses (`nm`) and with one instruction shape (`leaf_shapes()`: padding lines, `cs`/`ds`/`data16` prefixes and objdump comments dropped, immediates masked; CET's `endbr64` and AArch64's `bti c` are uniform and pass), and exactly one body per kernel name (a clone or duplicate fails). Tests 1–3 and 6 kernels must also have no conditional move/select (`cmov`; `csel`/`cset` family on arm64), no flag arithmetic (`setcc`/`sbb`/`adc`; `adc`/`sbc`/`ngc` on arm64) and no SIMD registers (Test 4's `sum_branchless` is checked for SIMD only). A data branch is a forward conditional branch that starts and lands inside a loop (between a backward branch and its target, so back-edges and early exits do not count) whose condition comes from data loaded in that loop: on x86-64 the nearest preceding flag-setting instruction is a `cmp`/`test` with a memory operand or reading a register last written in the loop by a `mov*` load; on aarch64 a `cbz`/`cbnz`/`tbz`/`tbnz` on, or a `b.cond` after a flag-setting `cmp`/`cmn`/`tst`/`ands`/`subs`/`adds`/`bics`/`ccmp`/`ccmn` reading, a register last written by `ldr*` (registers count by family, `%al`/`%rax`, `w3`/`x3`). The aarch64 rule runs in CI's arm64 jobs and locally on a cross build (`ARCH=aarch64 OBJDUMP=aarch64-linux-gnu-objdump`). Test 6's `correlate_distance` keeps the older rule: at least three forward conditional branches inside its loops (A, filler and B; mode `loop-branch3`); for it a `d == 0` guard inside the block loop could stand in for a lost B (current GCC drops that guard, because every caller passes d ≥ 4), so check that B is still its own branch after the filler loop. A pass is still necessary, not sufficient: a load-fed compare need not be the benchmark's condition, so read the inner loop's disassembly after codegen-relevant changes. `check_kernels.sh --counts <binary>` prints `id data_branches indirect_calls inner_loop_branches` for every kernel in `kernel_descs[]`, `correlate_distance` included (inner loop = the innermost loop that reads memory or calls indirectly), and `check_export.py --kernel-counts` fails if a kernel with declared counts is missing from that list; the job's "Kernel descriptors match the binary" step compares it with the export's `kernel` records (`kernel_descs[]` in `branch_bench.c`) through `check_export.py --kernel-counts`, and gcc-latest does the same. Fixtures prove each rejection still fires, each with its own message: [`.github/scripts/branchless_fixture.c`](.github/scripts/branchless_fixture.c) (branchless without any blacklisted instruction: `expected 1 data branch(es), found 0`), `loop_guard_fixture.c` (branchless sum plus an in-loop guard on the counter, which the older any-forward-branch rule accepted: `found 0`), `unrolled_fixture.c` (`#pragma GCC unroll 2` duplicates the data branch: `found` 2 or more), `asm_unrolled_fixture.c` (the same with a one-element asm data branch inside the unrolled C loop: `found` 2 or more), `merged_leaves_fixture.c` (`leaf_63` aliased to `leaf_62`: `63 distinct addresses for 64 leaves`), `uneven_leaves_fixture.c` (`leaf_63` is a plain `x ^ 1`: `2 instruction shapes for 64 leaves`) and, on x86-64, `jcc_fixture.S` (stub kernels, one 2-byte `jne` ending on a 32-byte boundary, built without `$JCC_FLAGS`: `check_jcc.sh` must list exactly that one hit). x86-64 and aarch64 only. Run it locally with `.github/scripts/check_kernels.sh ./branch_bench`. The job also runs [`.github/scripts/perf_test.c`](.github/scripts/perf_test.c), which includes `branch_bench.c` with `read()`/`ioctl()` replaced by stubs and checks the perf scaling and error paths without a PMU.
- **gcc-latest**: runs the gcc job's build (with the JCC alignment flags), small runs (default and `--hard`), `check_kernels.sh` and JCC check in the newest GCC image, pinned by tag and digest in [`.github/gcc-latest/Dockerfile`](.github/gcc-latest/Dockerfile) (the release workflow uses the same image). The Dockerfile is never built; it exists because Dependabot cannot update an image named in a workflow file. x86-64 only.
- **clang** (x86-64 and arm64): builds with the Clang flags and `-Werror`, runs the small size (also with `--hard`), runs `check_kernels.sh` and requires every FAIL to be Test 6's (its C kernel is branchless under Clang until Stage 3; at least one FAIL must appear, which proves the check still detects lost branches), so the asm kernels must keep their branches, and runs `clang --analyze` with `-analyzer-werror`.
- **sanitizers**: GCC ASan+UBSan (x86-64 and arm64) and Clang MSan, each running [`.github/scripts/smoke_test.sh`](.github/scripts/smoke_test.sh), which exercises every option, the report file and invalid input, and `perf_test.c`. Sanitizer builds are for correctness only; never use them for results.
- **sonarqube**: sets `kernel.perf_event_paranoid=1`, so real counters are used if the VM ever has a PMU. ## Code Architecture and Implementation Conventions

### 1. Function Inlining Prevention
All benchmark kernels (such as `sum_threshold`, `count_decisions`, `dispatch_indexed`, `sum_branchless` and `correlate_distance`) must be annotated with `__attribute__((noinline))`. This keeps the compiler from inlining hot loops into their callers. It does not stop other interprocedural optimizations, such as identical code folding (see section 5) or `.constprop` clones, so check the disassembly.

### 2. Dead Code Elimination (DCE) Prevention
Because benchmark loops compute values without external side effects during timing, the compiler could eliminate the loop entirely.
- Always retain or consume the computed output.
- Use `anti_dce_sink(u64 v)` (in [`branch_bench.c`](branch_bench.c)) on computed results. It stores the value into a file-scope `volatile u64` that is never read back; the compiler cannot elide a volatile store, so the computation stays.
- If a test performs an observable validation (such as Test 4's result comparison check), an additional `anti_dce_sink` call may be omitted.

### 3. Separation of Setup vs. Timed Execution
- Never allocate memory, perform I/O, or invoke the random number generator inside the timed measurement loop.
- Array generation, shuffling, and table initialization (e.g. `decisions_random`, `dispatch_indices`) must occur *before* starting the timer.
- Free all allocated resources once the benchmark passes complete.
- Read the `--size` global once at the start of each test (`const size_t len = size;`) and use `len` for the allocation, setup loops and kernel calls. Reading the global repeatedly makes static analyzers (SonarQube, `clang --analyze`) report out-of-bounds accesses, because they assume it may change between the `malloc` and the kernel call.

### 4. Deterministic and Low-Overhead PRNG
Use the local xorshift64 PRNG (`rng64()` / `rng_state`) instead of `stdlib rand()`. This avoids glibc locking overhead and distribution skew. Each `run_testN` starts with `seed_test(N)`, which sets `rng_state` to `test_seed(N, 0, 0)`; further input streams of a test take `test_seed(N, config, index)` (Test 5 uses `test_seed(5, 0, 0)`, Test 6 `test_seed(6, 0, 0)` for A and `test_seed(6, 0, 1)` for B). Seeds derive only from `--seed` (`base_seed`), the test number, the configuration and the index, so selecting or reordering tests never changes another test's input. Draw bounded values with `rng_below(bound)` (rejection sampling, no modulo bias), never `rng64() % bound`.

### 5. Indirect Dispatch and Identical Code Folding (ICF)
Test 3 generates 64 leaf functions via X-macros (`FOR_EACH_LEAF` / `DEF_LEAF`). Each leaf rotates its argument left by one and XORs it with its own constant, `LEAF_CONST(n)`: (n + 1) times the Weyl sequence step `0x9e3779b97f4a7c15ULL`, masked so every 16-bit chunk is in 1..0x7fff. The constants are distinct and nonzero, which prevents Identical Code Folding (GCC's `-fipa-icf`, on at `-O2`, or the linker's) from merging the function pointers into a single destination address, and they all need the same instructions (x86-64 `movabs`; AArch64 `mov` + three `movk`), so every leaf has the same shape and work. The rotation makes the result depend on the call order, so `dispatch_reference()` catches a call to the wrong target.

Test 1 and Test 4's branch rows call the same kernel, `sum_threshold`; there is no separate `sum_branch`.

### 6. Perf Timing Window Convention
- Measure a lone variant with `MEASURE(result, variant, kernel(args))` and a compared pair with `MEASURE_PAIR(ra, va, kernel_a(args), rb, vb, kernel_b(args), pair)`; `variant` is the row index in the test's `rows[]`. Each runs the `-n/--trials` loop; every measured trial (also with `-n 1`) goes through `MEASURE_TRAINED`, which first makes `TRAIN_RUNS` (1) untimed calls of the same kernel, then one `MEASURE_ONCE`, which calls `perf_start()` immediately *before* the `now_ms()` timer starts and `perf_stop()` immediately *after* it stops, and logs the trial. `MEASURE_PAIR` alternates the order per trial (`pair_a_first()`: AB, BA, ...), and stores the pair id for the summaries.
- Every measured trial is kept in `trial_log[]` (`TrialRecord`: test, variant, pair, run-wide `seq`, trial index, the stringized call and the `Result`); pairs are in `pair_info[]`. Both are static arrays sized for `--hard -n 99` (`MAX_TRIAL_RECORDS`, `MAX_PAIRS`); overflowing either is an internal error (exit 1). `main()` calls `begin_test(n)` before each test. A row's reported `Result` is `representative(test, variant)`: the median trial over all of that variant's trials, also across pairs.
- Comparisons come from the pairs, never from subtracting representative rows: `pair_stats(pair)` sums times over all pairs and signed counter differences (b − a) over valid pairs (both trials `PERF_OK`); `pair_cost()` turns that into the effective cost.
- The reported row is one real trial (the median by time, the lower middle one for even counts), never a per-field median, so time, cycles, branches and misses always belong together.
- Do **not** nest `perf_start()` or `perf_stop()` inside the `now_ms()` timing window; doing so introduces system call overhead into the wall-clock measurements.
- `MEASURE` is a macro, not a function, on purpose: the kernel must be called directly (not through a function pointer) so its codegen stays unchanged.
- Guard access to each counter slot in `r.counts[]` with `result_has(&r, CTR_BRANCHES)`, `result_has(&r, CTR_MISSES)` or `result_has(&r, CTR_CYCLES)`; any of them can be missing independently, and a trial's counts can be unusable even when the counter is open.
- Each `Result` carries its own counter metadata, set by `perf_stop()`: `perf_status` (one `PERF_*` reason on every path; `PERF_NONE` is 0, so a zeroed Result is never valid; `PERF_OK` is the only usable one), `counts[]` (scaled estimate), `raw_counts[]` (as read), `enabled_ns`/`running_ns` (this trial's scheduling deltas) and `open_mask`/`raw_mask` (snapshots of `perf_open_mask`/`perf_raw_mask`). `result_has()` tests `perf_status` and the result's own `open_mask`, not global state.
- Miss % is printed only when `miss_rate_valid()`: both counters valid, branches > 0, and `counter_semantics()` gives the same known population for both. x86 generic events are retired; on ARM, Linux v6.12 `drivers/perf/arm_pmuv3.c` maps generic branches to `BR_RETIRED` (0x21) or `PC_WRITE_RETIRED` (0x0C), both retired, but generic misses to the speculative `BR_MIS_PRED` (0x10), so ARM generic runs show "–"; the raw fallbacks 0x12/0x10 are both speculative and do get a rate. Other architectures are unknown.
- New counters go into the same group. Each needs a row in the `FOR_EACH_COUNTER` list (slot name, generic event as the `PERF_COUNT_HW_` suffix, ARM raw fallback, Markdown header, console label and width), which generates both its `CTR_*` slot and its `counter_descs[]` entry; its position in `counter_display_order[]` (`CHECK_LEN` fails the build when that list's length differs from `CTR_COUNT`); and an entry in `fake_perf.c`'s `fake_events[]` table (and `FAKE_PERF_EVENTS`). `perf_test.c` sizes its fake reads by `CTR_COUNT` and opens every counter, so it covers the new one unchanged; run it.
- Which counters are open is tracked in `perf_open_mask`, not by `perf_fd[]` values, so the zero-initialized state means "none open"; test it only through `perf_has()`.

### 7. Formatted Report Emission
Each test function receives `FILE *report` (which will be `NULL` if `-o` was not specified). Any new test should:
- describe its work per trial once, as `const Work work = { count, "elem" }` (or `"call"`, `"block"`), which drives the misses-per-item column;
- construct a `ReportRow` array (`{ label, result, work }`). Every initializer names `work`: `NULL` when the test's single `Work` applies, or a pointer to the row's own `Work` when rows do different amounts of work (it sets that row's misses-per-item; the column header keeps the unit of the `Work` passed to `emit_rows()`). `-Wextra` rejects an initializer that leaves it out;
- for standard 2-row (predictable vs. unpredictable) tests, measure both with one `MEASURE_PAIR` and call `emit_pair_summary(report, title, desc, rows, &work, pair)`, which emits the console rows, the Markdown table, the slowdown ratio and the effective-cost line;
- for multi-row tests (like Test 4), call `emit_rows(report, title, desc, rows, count, &work)`, `emit_pair_ratio(report, console_prefix, md_label, pair, suffix)` for each comparison ratio (pair b's summed time over a's; `emit_ratio()` is the plain formatter underneath), and `print_pair_cost(report, pair)`, then `printf("\n")` to end the test's console block (`emit_pair_summary` does this itself).

A test with a size rule calls `emit_skip(report, title, reason)` instead when the rule fails (Tests 5 and 6), and prints its heading first as usual. Call these after all `MEASURE`/`MEASURE_PAIR` calls. The console heading stays in `run_testN` before them, so progress shows while the kernels run.

This keeps console and Markdown output consistent from a single `ReportRow` definition. Labels in `ReportRow` may carry extra internal spaces for console alignment; `report_table()` automatically collapses multi-space runs when writing Markdown.

To wire up a new test, bump `NUM_TESTS` (leave `DEFAULT_TESTS` alone for an opt-in test, which then needs its own `expect 0 -t N` run in `smoke_test.sh` and a check that the default report lacks it), add `if (test_selected(N)) run_testN(report);` in `main()`, add N to `smoke_test.sh`'s `for t in 1 2 3 4` default-report loop (default tests only) and change its `expect 1 -t 7` invalid case to the new out-of-range number, add its kernel to `check_kernels.sh` if it must keep a branch, and add it to `check_jcc.sh`'s function list.

### 8. Output Stability, CLI and SonarQube Rules
- The default run (no options) keeps its console and report format; an opt-in option (`-n`, `-t`, ...) may only add output when it is used. Compare the default output with the previous build, numbers masked.
- Options are parsed one at a time in `apply_option()`; numeric values go through `option_number()`/`parse_count()` (range check, `K`/`M` suffixes). Keep functions small: SonarQube flags cognitive complexity above 25.
- Format `u64` with `PRIu64` and `size_t` with `%zu`.
- Integer literal suffixes `L`/`UL`/`ULL` are uppercase (SonarQube S818 flags a lowercase `l`); lowercase `u` is accepted.
- Write every integer-to-`double` conversion as an explicit `(double)` cast, also in mixed arithmetic such as `100.0 * (double)a / (double)b` (SonarQube S5276 flags implicit ones; the code is the same).
- Every file-scope symbol is `static`.

## Long-Term Goals

### Portability to more architectures (MIPS, RISC-V, PowerPC, ...)
The benchmark is developed and tested on x86-64 and ARM (Cortex-A72) Linux. Supporting other architectures is a long-term goal; known gaps:
- **CPU model detection:** `get_cpu_model()` only recognizes the x86 `model name` and ARM `Model`/`Hardware` keys in `/proc/cpuinfo`. MIPS uses `cpu model` (plus `system type`), PowerPC uses `cpu`, and RISC-V often has only `isa`/`uarch`, so these currently report "Unknown CPU".
- **Perf counters:** generic `PERF_COUNT_HW_*` events (branches, misses, cycles) are tried first everywhere, but raw-event fallbacks exist only for ARM. Many embedded MIPS cores have no PMU or no kernel PMU driver, so these fall back to wall-clock timing only.
- **Branch codegen:** `-fno-if-conversion` must still leave real branches in Tests 1–3, 5, 6 and Test 4's branch variant. Check the disassembly on each new architecture: MIPS has conditional moves (`movn`/`movz`, `seleqz`/`selnez` on R6) and RISC-V has `czero` (Zicond).
- **32-bit targets:** the `u64` accumulators and Test 3 leaf arithmetic become multi-instruction sequences on 32-bit cores (e.g. MIPS32), which changes the per-iteration work and makes timings incomparable with 64-bit results.
- **Memory footprint:** by default most tests allocate two 4 MiB buffers at a time, and Tests 2 and 6 three; on small embedded boards use `--size` (and `--reps` to keep run times sensible).
- **Interpretation:** README's interpretation section is written for deep out-of-order cores. In-order cores (common on MIPS) have much shorter misprediction penalties.
- **Validation:** cross-compile (e.g. `mips-linux-gnu-gcc`) and run under `qemu-user` to check correctness and output format. Timings under emulation are meaningless; real hardware is required for results.
